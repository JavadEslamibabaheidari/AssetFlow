# Milestone Plan: M2 - Core Inventory Domain

## Goal

Build the first production-shaped Inventory API domain for vendors, products, sales channels, and stock items, backed by PostgreSQL through EF Core and exposed through Minimal API endpoints that dispatch MediatR commands and queries.

## Scope

In scope:

- Implement the OpenAPI-designed resources from `contracts/openapi/inventory-api.yaml`: vendors, products, channels, and stock items.
- Add EF Core persistence for PostgreSQL with migrations for the inventory schema.
- Add a CQRS application layer using MediatR. API endpoints dispatch commands and queries; persistence is owned by handlers.
- Enforce the contract edge cases for validation, not-found, and conflict responses.
- Add risk-appropriate unit, integration, and endpoint tests.
- Keep Docker/local run paths usable for the API.

Out of scope:

- Reservations, allocation, stock holds, expiration, and oversell prevention. These start in M3.
- Kafka, outbox, event publication, channel workers, and marketplace synchronization. These start in M4.
- Authentication, authorization, tenant isolation, and admin UI.
- Update/delete endpoints. The M1 contract only includes create, get, and list operations.
- Advanced filtering, pagination, sorting options, or search beyond the filters already in the contract.

## Decisions

Decided:

- Use EF Core with the Npgsql PostgreSQL provider for application persistence.
- Use MediatR for command/query dispatch. Commands create vendors, products, channels, and stock items; queries list and fetch them.
- Keep the implementation in the existing `Inventory.Api` project for M2, organized by `Domain`, `Application`, `Infrastructure`, and `Api` folders. Split into multiple projects later only when complexity justifies it.
- Use Minimal APIs and route groups. Endpoint delegates map request/route/query data to MediatR requests and return HTTP results.
- Use database constraints plus handler checks for uniqueness and referential integrity. Handlers convert expected conflicts and missing references into API-level problem responses.
- Store `createdAtUtc` for vendors, products, and channels; store `updatedAtUtc` for stock items. Use UTC timestamps created by application handlers.
- For M2, `availableQuantity` equals `onHandQuantity`. Reservations will change this in M3.
- Use GUID identifiers generated by the application.
- Use `ProblemDetails` responses for validation, not-found, and conflict cases.

Deferred out of scope:

- Reservation-aware availability calculation.
- Event publication and outbox consistency.
- Multi-tenant ownership and permissions.
- API version negotiation beyond the current `/v1` contract base path.

Open questions:

- None.

## Deliverables

- EF Core model, DbContext, PostgreSQL configuration, and migrations for vendors, products, channels, and stock items.
- MediatR command/query request types and handlers for all M1 contract operations.
- Minimal API endpoint groups for `/vendors`, `/products`, `/channels`, and `/stock-items`.
- Consistent validation, not-found, and conflict problem responses.
- Tests covering success paths, validation failures, duplicates, missing references, filters, and persistence behavior.
- Updated docs and knowledge for M2 architecture and implementation status.

## Acceptance Criteria

- [ ] `POST /vendors`, `GET /vendors`, and `GET /vendors/{vendorId}` match the contract behavior.
- [ ] `POST /products`, `GET /products`, and `GET /products/{productId}` match the contract behavior, including vendor filtering.
- [ ] `POST /channels` and `GET /channels` match the contract behavior.
- [ ] `POST /stock-items`, `GET /stock-items`, and `GET /stock-items/{stockItemId}` match the contract behavior, including product/channel filtering.
- [ ] Duplicate vendor names, duplicate product SKUs per vendor, duplicate channel codes, and duplicate stock item product/channel pairs return `409`.
- [ ] Missing referenced vendors, products, channels, and stock items return `404`.
- [ ] Invalid request bodies and negative quantities return `400`.
- [ ] API endpoints dispatch MediatR commands/queries and do not access EF Core directly.
- [ ] EF Core persistence is backed by PostgreSQL provider configuration and migrations.
- [ ] Tests and CI pass.

## Risks and Mitigations

- EF Core and MediatR package adoption can ripple through the minimal service. Mitigate by adding the foundation first and keeping folders/namespaces explicit.
- PostgreSQL integration tests may require Docker availability. Mitigate by keeping handler tests deterministic and adding container-backed tests only where they verify persistence behavior that cannot be trusted in memory.
- Contract drift is likely while adding endpoints. Mitigate by mapping every endpoint and response to `contracts/openapi/inventory-api.yaml` during review.
- M3 availability behavior could be overfit into M2. Mitigate by making `availableQuantity = onHandQuantity` explicit and deferring reservations.

## Testing Strategy

- Unit: application result/error mapping, validation helpers, handler behavior where infrastructure can be substituted cleanly.
- Integration: EF Core persistence, uniqueness constraints, reference constraints, and endpoint behavior.
- Contract: compare implemented paths, status codes, and response shapes against `contracts/openapi/inventory-api.yaml` during review.
- Concurrency/failure: basic duplicate conflict coverage in M2; reservation concurrency is deferred to M3.

## Priority Decisions

- Critical prerequisite: persistence and CQRS foundation, because every endpoint depends on it.
- High value vertical slices: vendors first, then products, channels, and stock items. This order follows dependencies while producing usable API behavior early.
- Medium cleanup: final validation and docs after endpoint behavior is implemented.
